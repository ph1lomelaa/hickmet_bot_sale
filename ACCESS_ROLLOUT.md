# Смена пароля менеджеров с сохранением истории

При повторном входе обновляется доступ существующего пользователя по Telegram ID.
Профиль, имя, дата регистрации, брони, OPEN DATE и связи с историей сохраняются.
Новый Telegram-аккаунт — другой пользователь; автоматического переноса истории между аккаунтами нет.
Роли `admin` и `care` не требуют повторного ввода пароля при ротации пароля менеджеров.

## Настройки

В серверном `bull_project/.env` задайте выбранный владельцем новый пароль:

```dotenv
MANAGER_PASSWORD=<новый пароль>
MANAGER_ACCESS_VERSION=1
TELEGRAM_AUTH_MAX_AGE=43200
```

Не коммитьте `.env`. `API_TOKEN` должен быть одинаковым у API и worker.
Пароль обязателен, без пробелов по краям, и должен отличаться от паролей admin/care.
Прежний резервный пароль менеджеров удалён. Без обязательных настроек сервис не стартует.

Первый запуск добавляет nullable колонку `users.manager_access_version` без изменения
пользователей и броней. Старые менеджеры имеют пустую версию и проходят повторный вход.
Версия — HMAC от пароля и MANAGER_ACCESS_VERSION с ключом бота: сам пароль в БД не хранится.
В дальнейшем любая смена пароля автоматически отзывает старый доступ. Для отзыва без
смены пароля увеличьте MANAGER_ACCESS_VERSION. Не возвращайте прежнюю комбинацию пароля
и версии: она снова сделает старые записи доступа действительными.

## Порядок включения

1. Сделайте резервную копию рабочей БД. Например, в папке `bull_project`:

   ```sh
   docker compose exec -T db pg_dump -U bull -d bull_db > /secure/backup/bull-before-access.sql
   ```

   Используйте существующую защищённую папку резервных копий. Проверьте результат команды.
2. Подготовьте серверный `.env` с новым паролем и одинаковыми настройками у обоих сервисов.
3. Обновите опубликованные веб-страницы. Текущие ссылки бота ведут на отдельный
   GitHub Pages сайт `https://ph1lomelaa.github.io/book/`: изменение этого репозитория
   само по себе сайт не обновляет. В публикацию обязательно должны попасть `access.js`
   и все изменённые HTML из `bull_bot/webapp`, `admin_webapp`, `care_webapp`.
   Три копии `access.js` идентичны; сохраните существующую раскладку страниц и config.js.
   На короткое время обновления остановите worker и api, чтобы старый API не принимал записи.
4. Разверните новый код API и worker вместе:

   ```sh
   docker compose up -d --build --force-recreate api worker
   ```

   Только `restart` не подхватывает новые значения `.env`.
5. Проверьте `/health`, логи старта и вход менеджера. Старый пароль, старые кнопки и
   открытая до обновления форма не должны создавать брони. После нового пароля имя и
   вся история менеджера должны остаться прежними. Проверьте создание брони, загрузку
   паспорта, историю, OPEN DATE, страницы admin/care и скачивание паспортов.
6. Передайте пароль только нужным сотрудникам. После запуска worker менеджеры с устаревшим доступом получают приветствие и кнопку
   «🔑 Ввести пароль». Успешная отправка отмечается в БД: при обычном перезапуске
   уведомление повторно не отправляется. Сам пароль не рассылается. Если бот заблокирован,
   доставка невозможна; запрос повторного входа появится при следующем обращении к боту.
   При нажатии старых кнопок и /start показывается такое же приветствие.

Все `/api/` запросы теперь требуют подписанные Telegram initData и актуальный доступ.
Запуск веб-страниц вне Telegram и старые сторонние клиенты без заголовка
`X-Telegram-Init-Data` будут отклонены. Через 12 часов форму нужно открыть заново;
менеджер с действующим доступом при этом не обязан снова вводить пароль.
Паспортные ссылки выдаются на 2 минуты для конкретного файла и проверяют актуальность
доступа при скачивании. Внутренняя загрузка из worker имеет отдельную короткую подпись,
действующую только для `/api/passports/upload`.

## Проверки разработчика

```sh
python -m pip install -r bull_project/requirements.txt aiosqlite
python -m unittest discover -s tests -v
node --test tests/access-client.test.cjs
```

Python-тесты работают на отдельной временной SQLite БД, проверяют миграцию старой схемы,
повторный вход, сохранность профиля/истории, отзыв доступа, старые кнопки, API, подписи,
права на чужие брони, паспортные ссылки, ограничение попыток и роли admin/care.
OCR и Google Sheets в этих тестах не вызываются. PostgreSQL-миграцию и живой Telegram
нужно дополнительно проверить при развёртывании; эти локальные тесты их не заменяют.

Смена пароля не вводит проверку фактической оплаты. Любой получивший новый пароль
снова сможет войти; для индивидуальных запретов нужен отдельный список разрешённых ID.

Не откатывайте только API на старую версию после ротации: прежний код не проверяет
отозванный доступ. До исправления держите запись отключённой. Новая колонка может
оставаться в БД, удалять её для отката не требуется.

Уведомления отмечаются в `users.manager_access_notice_version`. Они не изменяют
доступ, профиль или брони. Возможен повтор при аварийном завершении между отправкой
Telegram-сообщения и сохранением отметки. Worker должен работать в одном экземпляре.
